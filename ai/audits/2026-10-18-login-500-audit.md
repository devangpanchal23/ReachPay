# Login 500 audit

**Date:** 2026-10-18  
**Scope:** Read-only review of the current workspace. No database, migration, or deployment was accessed. No `.env` file was opened. No existing file was changed for this audit.

## Summary

The current auth handler returns HTTP 500 only when an exception does not match its known migration, database availability, configuration, or rate-limit cases. A current `auth.failure` log should include a safe `reasonCode` and `requestId`. The reported response text matches the generic current 500 response, but the actual cause and deployed code cannot be identified without the matching Vercel log and deployment commit.

The login path needs PostgreSQL for its rate limiter, account lookup, session insert, and audit event. It does not call Twilio, SMTP, Resend, or Upstash. An incomplete auth migration can stop login, but recognized PostgreSQL missing-object codes return 503 in the current workspace code.

## Login path and status behavior

1. [src/site.jsx](/Volumes/T7/Devang/Code/Real_Project/ReachPay/src/site.jsx:130) posts JSON to `/api/auth/login` with same-origin credentials. The UI displays the safe `error` property from the response at lines 137-139 and 167-170.
2. [api/auth/[action].js](/Volumes/T7/Devang/Code/Real_Project/ReachPay/api/auth/[action].js:3) creates a request ID, sets no-store/security headers, checks request size and JSON content type, calls `handleAuth`, and catches errors from the entry handler.
3. [server/auth-controller.js](/Volumes/T7/Devang/Code/Real_Project/ReachPay/server/auth-controller.js:1093) checks request origin and method. Production POSTs require an allowed origin. A blocked origin returns 403.
4. Login rate checks run first: production limits are 10 per IP and 8 per identifier per 15 minutes at [server/auth-controller.js](/Volumes/T7/Devang/Code/Real_Project/ReachPay/server/auth-controller.js:788). The keys are HMAC hashed using `AUTH_RATE_LIMIT_SECRET`; the counters are stored in PostgreSQL.
5. The account SELECT at [server/auth-controller.js](/Volumes/T7/Devang/Code/Real_Project/ReachPay/server/auth-controller.js:835) reads email/mobile, password hash and salt, verification timestamps, status, role/access status, and whether another owner exists. Password verification uses Node `scrypt` at [server/auth-core.js](/Volumes/T7/Devang/Code/Real_Project/ReachPay/server/auth-core.js:26).
6. A verified account matching `OWNER_EMAIL` may be promoted only if no other owner exists. Login then inserts a new session and an audit record, and returns a 7-day cookie at [server/auth-controller.js](/Volumes/T7/Devang/Code/Real_Project/ReachPay/server/auth-controller.js:870).

| Outcome | Condition | Status |
|---|---|---:|
| Invalid credentials | Missing login fields, unknown account, or wrong password | 401 |
| Account policy block | Stored account status is locked or disabled | 403 |
| Origin policy block | POST origin is absent/invalid/not allowed in production | 403 |
| Rate limited | IP or identifier counter exceeds the configured limit | 429 |
| Known unavailable/configuration condition | Required DB config, recognized DB connectivity error, migration SQLSTATE, or auth rate secret missing | 503 |
| Unexpected or unclassified exception | Any thrown error not recognized by the safe mapper, including many SQL errors outside the migration/availability allowlists | 500 with a generic response |

The login catch at lines 878-880 rethrows in production, so the outer `handleAuth` catch logs and maps the error. There is no single proven reason for this production request yet. If the current revision served it, a 500 points to an unclassified exception or SQLSTATE, not the explicitly recognized missing-schema cases. An older deployed revision is also possible.

## Dependencies and owner behavior

- **Database:** Required in production. Login uses PostgreSQL for the rate limiter, account lookup, owner promotion when applicable, session insert, and audit insert. A missing auth schema can therefore block login.
- **Redis:** Auth routes do not call Upstash. Login rate limits use PostgreSQL. Upstash variables are used by `server/contact-handler.js` for contact-form rate limiting only. Missing Redis does not break login.
- **SMS/email:** Login imports provider modules but does not validate or call Twilio, SMTP, or Resend. Twilio validation occurs only when sending or checking mobile OTP. Email delivery code runs only on the email OTP path. No import-time provider network call or credential check was found.
- **Pool and Neon:** Production pool is configured with one connection per warm function, 10-second idle timeout, 3-second connect timeout, and a module-level reusable pool at [server/auth-controller.js](/Volumes/T7/Devang/Code/Real_Project/ReachPay/server/auth-controller.js:83). Neon URLs retain channel binding and TLS certificate verification (`enableChannelBinding`, `rejectUnauthorized: true`) in [server/database-config.js](/Volumes/T7/Devang/Code/Real_Project/ReachPay/server/database-config.js:24). No database URL was displayed or tested.
- **Owner bootstrap:** No separate owner table is used. If migration 002/003 has not run, a verified active configured owner may be promoted on login only when no other owner exists. An unverified mobile keeps the session limited and delays owner powers. Existing active, verified stored owner role remains recognized even if `OWNER_EMAIL` later differs. The unique partial index and trigger enforce one protected owner after migration 002. If those objects are missing or production has inconsistent preexisting rows, actual protection is To be confirmed by the schema checker and private database review.
- **Owner lockout:** App team operations exclude owner accounts from approve/revoke/remove targets. The database trigger protects the current owner from deletion, demotion, revocation, or lock. The owner intentionally has no owner powers until active and both contact methods are verified. These protections rely on migration 002 being present.
- **Partially verified session:** Login creates a session for valid credentials regardless of mobile verification and sends the user to `/auth/verify`. `currentUser` resolves an unverified account to `limited`; `hasTransactionAccess` requires active status and both verified timestamps. Financial and beneficiary APIs check this on the server. The Vercel catch-all also denies limited roles. The dashboard UI redirects a user whose `/me` response has `dashboardAllowed=false`. Direct static pages can still load the SPA shell; protected data/API access is server-checked. The verification page can use authenticated mobile resend/verify and sign out. This behavior is present in the current workspace; the deployed version is To be confirmed.

|---|---|
| Cookie | `reachpay_session`; HttpOnly, Secure in production, SameSite=Lax, Path=/, 7-day Max-Age. Logout clears it. |
| Token handling | New random token per login; DB stores SHA-256 token hash. Existing sessions are not revoked on a later login. |
| CSRF/origin | Non-GET auth actions require `originOk`; production compares against `PUBLIC_SITE_URL` when set, otherwise forwarded host/protocol. Missing Origin fails in production. GET `me` is exempt. |
| Rate limits | Login: IP 10/15m, identifier 8/15m. Production counters in PostgreSQL; HMAC keys use `AUTH_RATE_LIMIT_SECRET`. |
| Enumeration | Wrong password/unknown account share 401. Locked/disabled account returns 403, which reveals a policy state. |
| Failure responses/logs | Generic response for unexpected error; structured auth logger records event, request ID, context, and reason code only. It does not log request bodies, passwords, OTPs, cookies, tokens, connection strings, keys, or phone values. |
| OTP | Email challenge stores HMAC, expires after 10 minutes, and counts attempts. Twilio Verify handles mobile codes. Mobile provider errors are mapped to safe reason codes. |
